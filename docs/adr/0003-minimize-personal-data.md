# ADR-0003: 預かる個人情報を最小限にし、預かるものは暗号化・記録・期限付きで扱う

- ステータス: 提案中
- 日付: 2026-11-05
- 決定者: 小田 裕貴
- 関連: ADR-0001、ADR-0002

## コンテキスト

- 扱うのは子ども(選手)と保護者の情報である
- 運営は個人で、セキュリティ専任者はいない。漏えいした場合の影響は大きく、ポートフォリオとしても逆効果になる
- 当面はデモ環境のみを公開し、実ユーザーは受け入れない。ただし、実ユーザーを受け入れても問題のない設計にしておく
- 守るべき情報を減らすことが、最も確実で安い対策である

## 決定

### 1. 持たない情報

次の情報は、項目として用意しない。

- 住所、電話番号
- 生年月日(学年で代替する。学年は年度替わりに一括で繰り上げる)
- 健康情報(アレルギー・既往歴など)
- 写真
- 学校名
- 決済情報(オンライン決済はしない)

### 2. 持つ情報と扱い

| 情報 | 用途 | 扱い |
|---|---|---|
| 選手の表示名(呼び名でも可) | 名簿・出欠 | 項目単位で暗号化 |
| 選手の学年・背番号 | 学年宛てのお知らせ・並び替え | 平文(個人を特定しにくいため) |
| 保護者の表示名 | 名簿 | 項目単位で暗号化 |
| 保護者のメールアドレス | ログイン・通知 | 項目単位で暗号化。ログイン時の照合用に、別途ハッシュ値(ブラインドインデックス)を持つ |

### 3. 記録と期限

- 個人情報の閲覧・変更・CSV出力を監査ログに残す(誰が・いつ・何を)
- 退会・卒団から1年経過したデータは、定期処理で削除する
- アプリのログやエラー通知に個人情報を出さない。出力前に伏せ字にする仕組みを入れ、テストで確認する

### 4. 配信サービス(notify-relay)での扱い

- 宛先のメールアドレスは配信処理の間だけ保持し、配信記録にはハッシュ値だけを残す
- 配信記録そのものも、7日で削除する。既読・失敗などの利用者向けの状態はLaravel側が持つため、Go側の記録は二重配信の防止と障害調査にだけ使う。週末に起きた障害を週明けに調べられる長さとして7日とする

### 5. デモ環境

- デモ環境には架空のデータだけを入れる。実在の人物の情報は入れない
- デモ環境から外部へのメール送信はしない

## 検討した選択肢

| 案 | 内容 | 評価 |
|---|---|---|
| A | 一般的な名簿アプリと同様に、住所・電話番号・生年月日なども持つ | 機能は作りやすいが、守るべき情報が増え、個人運営では責任を負いきれない |
| **B** | **持つ情報を最小限にし、持つものは暗号化・記録・期限付きにする** | **漏えい時の影響を構造的に小さくできる** |
| C | 個人情報を一切持たない(全員匿名) | 名簿として役に立たず、ログインもできない |

## 結果

良くなること:

- 漏えいしたときの影響が小さくなる。持っていない情報は漏れない
- 「何を持たないか」を設計段階で決めた記録として、面接で説明できる

悪くなること・受け入れるコスト:

- 誕生日のお祝いや緊急連絡先など、一部の便利機能は作れない
- 暗号化した項目では、名前の部分一致検索ができない。名簿の検索は学年・背番号での絞り込みと、画面上での絞り込みで代替する
- 暗号鍵の管理と、鍵の入れ替え(ローテーション)の手順が必要になる。手順書(runbook)に残す

## 見直す条件

- 実ユーザーを受け入れることになり、利用者から必須の要望(例:緊急連絡先)が出た場合。そのときは、追加する項目ごとに新しいADRで判断する
