# ADR-0002: 通知の配信をGoの独立サービス(notify-relay)に切り出す

- ステータス: 提案中
- 日付: 2026-11-05
- 決定者: 小田 裕貴
- 関連: ADR-0001

## コンテキスト

通知には次の性質がある。

- 雨天中止の連絡などで、朝6時台に多くのチームの送信が同時に集中する(目標:30万通を10分以内、つまり毎秒約500通)
- 通知はメールだけで送る。メール送信サービスには送信レートの上限があり、一時的に失敗することがある
- 同じ通知が二重に届くと、保護者の信頼を損なう
- 配信が止まっても、名簿やお知らせの作成などの業務機能は止めたくない
- デモ環境はメモリ2GB程度のVPS1台で、配信のためだけにメモリを大きく使えない

## 検討した選択肢

| 案 | 内容 | 評価 |
|---|---|---|
| A | Laravelのキューワーカーで配信する | 実現は可能。ただし並行数を上げるにはワーカープロセスを増やす必要があり、1プロセスあたりのメモリが大きく、2GBのVPSでは並行数を稼ぎにくい。配信の障害がLaravelのワーカー全体に波及する |
| **B** | **Goの独立サービスで配信する** | **軽量な並行処理(goroutine)で、少ないメモリで高い並行数を出せる。障害を配信に閉じ込められる** |
| C | 外部の通知SaaSを使う | 実装は最小だが、費用がかかり、流量制御や二重配信防止を自分で設計した証明にならない |

正直に記録しておく点:案Aでも、ワーカーを十分に増やせば目標は達成できる可能性がある。Goを選ぶ理由には、限られたメモリでの並行性能と障害の分離に加えて、Go案件向けに配信基盤の設計力を示すというポートフォリオ上の目的も含まれる。

## 決定

案Bを採用し、notify-relay をOSSとして公開する。

notify-relay の責務:

- Laravelから配信依頼(宛先リスト・テンプレート・重複防止キー)を受け取る
- メールを並行送信する。送信はSMTPで行い、ローカルとデモ環境ではMailpit、実運用ではメール送信サービスに切り替える(コードは同じ)
- 送信先サービスの上限に合わせた流量制御、失敗時の再送(指数バックオフ)、上限を超えた失敗の記録
- 重複防止キーによる二重配信の防止(同じキーの依頼は1回だけ処理する)
- 配信結果をLaravelへwebhookで通知する

notify-relay がやらないこと:

- 業務ロジック(誰に送るかの判断、権限、テンプレートの文面の決定)
- LaravelのDBの参照
- 宛先の個人情報の長期保存(ADR-0003)

Goが止まっているときの扱い:

- Laravelは配信依頼をいったん自分のDBの送信待ちテーブル(アウトボックス)に記録し、そこからGoへ送る
- Goが止まっていれば送信待ちのまま保持し、復旧後に再送する
- 再送しても二重に届かないよう、すべての依頼に重複防止キーを付ける

サービス間の通信:

- Laravel→Go、Go→Laravelのどちらも、共有鍵による署名(HMAC)とタイムスタンプを付け、受信側で検証する。古いタイムスタンプは拒否して、なりすましと再送攻撃を防ぐ
- 1通の通知を、サービスをまたいだトレースIDで配信先まで追跡できるようにする

## 結果

良くなること:

- 配信の負荷と障害が業務機能から切り離される
- 流量制御・再送・二重配信防止を一か所に集約でき、負荷試験と障害訓練の対象が明確になる
- notify-relay は他のアプリからも使える汎用の部品になる

悪くなること・受け入れるコスト:

- 通知の流れが2つのサービスにまたがり、障害時の調査が難しくなる。トレースIDで対処する
- アウトボックス・署名・webhookの実装が必要になり、モノリスより作るものが増える
- 配信APIの互換性を、バージョンを付けて管理する必要がある

## 見直す条件

- 負荷試験で、Laravelのキューだけでも目標を同等の資源で満たせると分かった場合(その結果も記録する)
- notify-relay の運用が開発時間を圧迫し続けた場合
