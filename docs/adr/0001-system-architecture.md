# ADR-0001: システム構成を Laravel API + React SPA + Go 配信サービスの3つに分ける

- ステータス: 提案中
- 日付: 2026-11-05
- 決定者: 小田 裕貴

## コンテキスト

少年スポーツチームの運営ツール(名簿・連絡・出欠・当番・会費)を作る。前提は次のとおり。

- 利用者の大半は保護者で、スマホのブラウザから使う。ネイティブアプリは作らない
- 通知はメールだけにする(Webプッシュ・LINEは使わない)
- 朝6時台など、特定の時間に大量の通知が集中する(目標:30万通を10分以内に送信)
- 開発者は1人で、開発時間は週10時間程度
- Laravel案件とGo案件の両方で、設計から運用までの力を示すポートフォリオにする
- 費用は最小限にする。デモ環境はVPS1台(メモリ2GB程度)を想定

## 検討した選択肢

| 案 | 内容 | 評価 |
|---|---|---|
| A | Laravelモノリス(Blade または Inertia)+ Laravelのキューで配信 | 最も早く作れる。ただし配信の負荷と業務処理が同じプロセス群で競合し、配信の障害が画面に波及する。Goを使う理由がない |
| **B** | **Laravel API + React SPA + Go配信サービス** | **業務ロジックと配信を分離できる。サービスは3つに抑えられる** |
| C | すべてGoで実装 | Laravel案件向けの証明にならない。名簿・権限などの業務機能はLaravelのほうが速く安全に作れる |
| D | 機能ごとに細かくマイクロサービス化 | 1人・週10時間では運用しきれない。過剰設計 |

## 決定

案Bを採用する。

| リポジトリ | 技術 | 役割 |
|---|---|---|
| team-ops-api | Laravel(API専用、Sanctum、OpenAPI) | 唯一の窓口。認証・権限・マルチテナント・業務ロジック・業務データを持つ |
| team-ops-web | React SPA(スマホ優先) | Laravel APIだけを呼ぶ |
| notify-relay | Go(OSS、内部サービス) | 配信依頼を受け、メールを並行送信する |

連携ルール:

- フロントはGoを直接呼ばない。GoはLaravelのDBを読まない。Goに業務ロジックを入れない
- Laravel→Goは配信API、Go→Laravelは結果のwebhook。サービス間の通信は署名付きにする(詳細はADR-0002)
- 配信APIの仕様の正本は notify-relay のOpenAPIとし、Laravelは使うバージョンを固定する

認証:

- SPAとAPIは同じ親ドメインのサブドメインに置き(例:app.〜 と api.〜)、Sanctum のCookieベースのSPA認証を使う。トークンをブラウザのストレージに置かない
- ログインはメールのマジックリンク(パスワードなし)

フロントにReactを選ぶ理由:

- 開発者はVue.jsの経験があるが、あえてReactを選ぶ
- 採用企業・案件の数が最も多く、案件獲得の選択肢が広がる(キャリアの汎用性)
- 情報量とライブラリが豊富で、問題の解決策を見つけやすい。周辺ツールの選択肢も多い
- 将来ネイティブアプリが必要になった場合、React Nativeで知識を活かせる
- 受け入れるコスト:Vue.jsより習熟に時間がかかる。設計の型(状態管理・データ取得)を最初に決め、CLAUDE.mdに明記して、AIの出力のばらつきを抑える

## 結果

良くなること:

- 配信の負荷や障害が、名簿や権限などの業務機能から切り離される
- Laravel・Go・フロントのそれぞれで、役割がはっきりした成果物を示せる
- APIがOpenAPIで定義されるので、フロントとバックエンドの契約が明確になる

悪くなること・受け入れるコスト:

- リポジトリが3つになり、CI・依存更新・リリースの手間が増える
- サービス間の契約(API・webhook)の互換性を管理する必要がある
- ローカル開発で3つを同時に動かす必要がある。docker compose で一発起動できるようにして対処する

## 見直す条件

- 配信の要件が「チーム内の数十通」程度に縮小し、Goを分ける利点が運用コストを下回った場合
- 運用の手間が週10時間の開発時間を圧迫し続けた場合
