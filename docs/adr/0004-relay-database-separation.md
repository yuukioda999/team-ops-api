# ADR-0004: notify-relay のデータは同じMySQLサーバー内の専用スキーマに置く

- ステータス: 承認
- 日付: 2026-11-05
- 決定者: 小田 裕貴
- 関連: ADR-0001、ADR-0002

## コンテキスト

- notify-relay は、配信待ちの依頼・重複防止キー・配信記録を保存する必要がある。再起動しても送りかけの通知を失わず、同じ依頼を二重に処理しないため
- 「GoはLaravelのDBを読まない」というルールを、口約束ではなく仕組みで守りたい
- 費用は最小限にする。デモ環境はメモリ2GB程度のVPS1台

## 検討した選択肢

| 案 | 内容 | 評価 |
|---|---|---|
| A | Laravelと同じスキーマに notify-relay のテーブルも置く | 最も簡単だが、Goから名簿などのテーブルが読めてしまう |
| **B** | **同じMySQLサーバーに専用スキーマを作り、接続ユーザーを分ける** | **費用・メモリはほぼ増えず、権限でアクセスを分離できる** |
| C | notify-relay 専用に別のDB(Redis、別のMySQLなど)を立てる | 分離は最も強いが、2GBのVPSではメモリが足りず、運用対象も増える |

## 決定

案Bを採用する。

- MySQLサーバー内に `team_ops`(Laravel)と `notify_relay`(Go)の2つのスキーマを作る
- 接続ユーザーを分け、それぞれ自分のスキーマにだけ権限を与える
- スキーマをまたぐ参照や結合はしない。データの受け渡しは配信APIとwebhookだけで行う

## 結果

良くなること:

- 「GoはLaravelのDBを読まない」が権限で強制される
- サーバー代とメモリがほぼ増えない
- 将来 notify-relay を別サーバーに移すとき、自分のスキーマだけを移せばよい

悪くなること・受け入れるコスト:

- MySQLサーバーが止まると両方のサービスが止まる(デモ環境では許容する)
- 負荷が高いとき、片方の重いクエリがもう片方に影響しうる。負荷試験で確認する

## 見直す条件

- 負荷試験で、notify-relay の書き込みがLaravelの応答速度(p95 300ms)を悪化させると分かった場合
- 実ユーザーを受け入れ、可用性の要求が上がった場合
