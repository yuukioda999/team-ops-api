# プロジェクト立ち上げ依頼:少年スポーツチーム運営ツール

## あなたの役割
私(フリーランスのWebエンジニア、PHP/Laravel・Goで実務5年)の開発パートナーとして、要件定義から運用保守までの全工程を、AI駆動開発で一緒に進めてください。実装は主にあなたが担当し、私は仕様・設計判断・レビューを担当します。

## 目的
- 少年野球・サッカー等のチーム運営(名簿・連絡・出欠・当番・会費)をスマホで回せる無料Webサービスを作る
- 公開形態は「①ローカルでDocker一発起動」と「②デモ環境の公開」の2つ。実ユーザーの受け入れは行わない(将来の選択肢として残す)
- Laravel案件・Go案件の面接で使うポートフォリオにする。全工程の成果物とAI駆動開発の記録を公開リポジトリに残す
- マネタイズはしない

## 前提・制約
- 開発時間は週10時間程度
- 第1弾は2027年1月にデモ環境として公開する
- デモ環境:「デモとしてログイン」を押すたびに架空データの見本チームを訪問者専用に複製する(ADR-0005)。各デモチームは24時間で削除し、毎晩期限切れ分を掃除する、外部へのメール送信はしない(送信内容は画面で確認できるようにする)
- 費用は最小限にする。サーバーは後で決める(候補:さくらのVPS 2GB 月払い)
- 判断に迷う点は推測で進めず、選択肢と推奨を示して私に確認すること
- 設計判断はすべてADRに残すこと

## システム構成(決定済み)
| リポジトリ | 技術 | 役割 |
|---|---|---|
| team-ops-api | Laravel(API専用、Sanctum、OpenAPI) | 唯一の窓口。認証・権限・マルチテナント・業務ロジック・業務データ |
| team-ops-web | React SPA(スマホ優先) | Laravel APIだけを呼ぶ |
| notify-relay | Go(OSS、内部サービス) | 配信依頼を受け、メールを並行送信。流量制御・再送・二重配信の防止・結果webhook |

連携ルール:
- Laravel→Goは配信API(宛先リスト・テンプレート・重複防止キー)、Go→Laravelは結果webhook。サービス間は署名付きリクエストにする
- API仕様の正本はnotify-relayのOpenAPI。Laravelは使うバージョンを固定する
- フロントはGoを直接呼ばない。GoはLaravelのDBを読まない。Goに業務ロジックを入れない
- Go通知基盤は第1弾から使う

## スコープ
- 第1弾(〜2027/1):チーム作成、招待(URL・QR、7日有効、役員の承認制)、名簿(選手と保護者の紐づけ、CSV取込、エラー行表示)、役割ごとの権限(代表/役員/コーチ/保護者)、お知らせ(全員・学年・役割宛て、予約送信)、既読・配信失敗の一覧と未読者への再通知。Go側は配信API・メール送信・再送・二重配信の防止・webhook。デモモード(訪問者ごとのデモチーム、24時間で自動削除、送信内容の画面表示)
- 第2弾(2027/2〜4):予定、出欠と自動催促、雨天中止の一斉連絡。Go側は流量制御・チーム間で公平な順番制御
- 第3弾(2027/5〜):当番・配車の自動割当、会費の請求と入金記録、年度引き継ぎ・学年繰り上げ・卒団
- やらないこと:メール以外の通知チャネル(Webプッシュ・LINE等)、オンライン決済、住所・生年月日・健康情報の保持、チャット、ネイティブアプリ、成績管理
- 認証:メール+マジックリンク(パスワードなし)

## 非機能要件(目標値。負荷試験で検証する)
- 朝6時台に30万通を10分以内に送信完了(想定規模:1万チーム×30人)
- 主要APIのp95が300ms以下。月間稼働率はAPI 99.5%、配信成功率 99.9%
- Goが停止したらLaravelが配信依頼を保持し、復旧後に再送する(二重配信はしない)
- テナント分離:全クエリにチームIDの絞り込みを強制し、他チーム参照をテストで検出する
- 選手名・連絡先は項目単位で暗号化。閲覧・変更・出力を監査ログに残す。退会・卒団後1年で削除
- 監視:サービスをまたいだトレースIDで、1通の通知を配信先まで追跡できること

## 決定事項(2026-11-05)
- 対象競技:作りは競技を問わない形にし、集客・デモデータ・画面の文言は少年野球に寄せる。役割や当番の呼び名はチームごとに変更可能にする
- インフラ:デモ環境は月額固定のVPS1台(費用最小)。フロントは静的ホスティングの無料枠(Cloudflare Pages等)。監視はGrafana Cloud無料枠。AWS ECS構成はTerraformのコードとplanまで(applyしない)。具体的なサーバーは後で決める
- メール:ローカルとデモ環境では外部送信せず、Mailpit等で受け止めて画面で確認する。外部送信サービス(Amazon SES等)は実ユーザーを受け入れる場合に選定する
- 負荷試験:自分のPCでモック相手に実行し、結果をリポジトリに残す
- 通知チャネル:メールだけにする(2026-11-05決定)。ログインのマジックリンクと仕組みを共通化し、iPhoneでも設定不要で届くため
- ローカル環境:本番相当のことをすべてローカルで再現できるようにする。メールはMailpitで受け止め、Mailpitの障害注入機能(Chaos)でSMTPエラーを起こして再送・障害訓練を行う。監視はローカルにもGrafana一式(トレース・メトリクス・ログ)を立て、デモ環境と同じダッシュボードで確認できるようにする
